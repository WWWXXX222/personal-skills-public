# 工作流与产物

## 运行目录

选用户指定目录，或在工作区创建 `okr-runs/<company-slug>-<period>-<run-id>/`。不要写到安装 skill 的目录。恢复时使用同一个目录；新运行不覆盖旧运行。

最小产物：

```text
run.md                 运行契约、阶段、预算、停止原因
context.md             事实、约束、来源及冲突索引
baseline/              原稿副本或不可变引用与内容哈希
candidates/a.md        独立提案；b.md、c.md 同理
reviews/               按轮次和评审视角分别保存
revisions/             每轮稿件，不覆盖历史
recommendation.md      推荐稿，包含每个 KR 的稳定 ID
okr.json               最终推荐稿对应的结构化检查输入
verification.json      检查脚本输出
decisions.md           选择、采纳、拒绝、目标变化及依据
handoff.md             变更说明、待核实与待决事项、最终验收
```

文件可以合并以减少重复，但原稿、推荐稿、结构化输入和证据追溯必须能区分。现有证据可按路径引用，不复制整座公司资料库。

## 运行契约

开始提案前写清：

- 用户的目标、周期、工作范围和输出语言。
- 基线及其哈希、允许读取的来源、已确认决定、冲突与数据缺口。
- 可更改的目标结构与可提议但未授权实施的经营决定。
- 固定的验收维度、关键约束和原始目标；不为追求分数逐轮改标准。
- 默认 3 候选、最多 3 轮修订、1 次最终验收；用户的时间或成本上限优先。
- 实际 agent 并发数、模型、是否支持独立上下文。最多主控加 3 个活跃子 agent，空出的槽位可复用。
- 当前阶段、已完成产物、未解决问题、下一步；每次阶段变化更新，便于中断恢复。

向用户简短说明默认假设后继续。只有缺少信息会导致整个任务目标不明、且无法合理推断时才请求澄清；事实缺口通常以有条件草案继续。

## 来源底稿

每条关键事实或约束记录：稳定 ID、具体说法、来源定位、日期、确认状态、适用范围、冲突。原始记录中的“有人提出”只证明该提议存在，不证明它已获批准。

默认优先核对明确的用户修订和正式批准记录，再看原始业务数据、会议记录、摘要、历史草案。不同材料在不同事实领域的权威性可以不同。不要以文件名、修改时间或引用次数替代判断。

## 比较和修改

候选比较采用验收维度逐项说明，不用单个总分替代经营取舍。硬约束不通过的候选不能因为文风好被选中。若多个候选均不可行，先定位共同缺失的假设或资源，修正任务框架并计入预算，不无限重开 arena。

决策记录一行包含：轮次、KR/问题 ID、选择、理由、证据、原值→新值、确认状态、遗留影响。不要记录私有推理过程；保留可审阅的理由即可。

评审提出的选择偏好必须与可证实缺陷分开。主控可以拒绝意见，但要注明上下文和理由。有力的单一反例必须处理，多数同意不能推翻反例。

每轮改稿后主控按同一验收规则检查，并将实际变更交回对应独立评审者复核。重大结构变更复核全稿；局部修复重点核对相关指标、依赖与回归风险。复核仍有问题时进入下一轮，不能只记录主笔自评。

## 停止与状态

- **REVIEW_READY**：结构检查无错误或未确认字段；独立评审未发现未解决的重大矛盾；关键资料、口径、容量和责任有依据。仅表示可提交管理层审阅，不代表已批准或战略必然正确。
- **CONDITIONAL**：完成可完成的修订，仍有影响目标、资源或责任的资料缺口／经营选择。推荐稿明确条件、备选和影响。缺数据没有变成虚构值。
- **INCOMPLETE**：达到预算或被明确停止，仍有可修复的重大缺陷、缺失必要产物或未完成验收。交付当前最佳版本和续接信息，不冒称完成。

提前结束条件：达到验收要求；或连续两轮没有实质改善且剩余问题已转为明确缺口或经营选择。默认三轮上限是预算，不是质量证明。最后一次验收若发现问题且预算用尽，标记 CONDITIONAL 或 INCOMPLETE，不能偷偷再开无限循环。

## 最终呈现

先给推荐结论，再给相对原稿的变化、少量关键选择、全部数据缺口的链接以及验收范围。关键选择附推荐、备选、代价与建议决策人。没有证据支持的目标可保留为候选，但不得包装成已确认计划。
