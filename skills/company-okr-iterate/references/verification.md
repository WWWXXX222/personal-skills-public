# 公司级 OKR 验收规则

本文件定义人工与 agent 评审标准。固定后应用于原稿、候选和修订稿；脚本仅覆盖其中可机械检查的子集。

## 六个维度

| 维度 | 验收问题 | 缺陷证据示例 |
| --- | --- | --- |
| 战略聚焦 | 是否表达本周期的关键取舍？公司级目标与部门任务是否分层？ | 所有探索都标最高优先级，却没有放弃项或投入限制 |
| 商业因果 | 完成 KR 后，目标客户或经营结果有什么变化？ | 以开工、开会或上线直接证明收入、PMF 或效果提升 |
| 指标可核验 | 定义、单位、对象、时间窗、基线、目标、证据来源是否齐全且一致？ | 把季度客户续约率与年度收入留存比较；ARR 与当季收入混算 |
| 资源可行 | 同一资源是否重复承诺？关键路径、外部依赖和容量有依据吗？ | 两个同期限项目都假设可独占同一团队；招聘未到岗却按满产能估算 |
| 责任清楚 | 每个 KR 是否有唯一最终负责人、依赖方承诺和验收方式？ | 多个“共同负责”但无人裁决；技术交付者被视为所有收入缺口负责人 |
| 证据与约束 | 事实、批准决定、讨论值和建议是否分开？原有决定是否被悄悄改写？ | 持续扣款被当成有效活跃；历史候选数字变为正式承诺 |

## 必须核对的关系

- 收入桥：期初 + 新签 + 扩张 − 缩减 − 流失应与期末目标同币种、同口径。收入、商机金额与潜在影响金额不可混为一项实绩。
- 留存：客户数与收入留存分开；固定 cohort、分母和观察窗；GRR/NRR 不包含新客收入。没有分母的数据不能编成可靠百分比。
- 交付：里程碑可以作为使能型 KR，但写明支持的结果和可验收条件。不是所有基础建设都必须强行归因到季度收入。
- 探索：明确客群、样本或招募条件、观察窗口、预算边界、成功/调整/停止判据。允许验证失败；不提前承诺必然获得 PMF。
- 效率与成本：区分理论释放产能、实际增产与真实成本节约；总成本与单位成本并列检查，保留质量和可靠性护栏。
- 资源：列项目、负责团队、人月或已知容量、日期和冲突。无数据则为未知；不能由 AI 估算人数并称为批准预算。
- 目标变化：保留基线版本、原目标、变更理由和状态。不能通过更换窗口、分母、删除困难 KR、降低目标或改 rubric 来伪造改善。
- 历史反馈：核对明确的业务优先级、职责修订和已否决项。上下文相关的决定不得泛化为永久政策。

## 发现格式

每条发现包含：ID、所在 KR/位置、严重程度、问题类型、具体证据或情景假设、业务影响、建议处理、可检查的关闭条件。

严重程度分为：重大（会改变取舍、资源或结果解释）、一般（影响执行但可局部修复）、编辑性。问题类型分为：缺陷、事实缺口、经营选择、偏好。无法由现有证据判定的内容明确列为缺口或选择，不假装为已证实缺陷。

拒绝无依据的“再加一个目标”“把指标调高”“多开会”等意见。无需为凑数输出发现。

## 最终独立验收

验收者读取最终稿、结构化 JSON、原稿、运行契约、决策记录及关键原始证据，不能只读主控摘要。

1. 实际打开关键来源，核验数值、语境、确认状态与日期。无法访问的来源不能凭引用通过。
2. 逐个核对 Markdown 与 JSON 的 KR ID、目标、负责人、状态、期限，发现不一致退回主控。
3. 重算可以重算的指标关系；检查重复收入计数、时间窗、依赖与资源冲突。
4. 对照原稿及运行契约检查遗漏、目标放宽、范围改变和历史决定回归。
5. 读已拒绝意见，检查是否错过有证据的少数意见。
6. 给出 REVIEW_READY、CONDITIONAL 或 INCOMPLETE，附残余问题和实际覆盖范围。

独立评审只能检查方案的逻辑与证据。客户会不会续约、实验能否成功、战略是否最优仍须真实业务反馈。模型自评分数不能作为这些结论的证据。
